# Goal

Ship the site's centerpiece: a continuous, scrollable feed over every one of the `52!` deck orderings. Each row is a full 52-card deck rendered as **real playing cards fanned left to right** (public deck number plus all 52 cards, each face's pips and court design visible). A visitor can scroll through the space and jump directly to any deck number via a shareable URL.

# Non-Goals

- The drag-and-drop deck editor and its randomize shuffle (separate plan, decision 0006).
- Favorites, social preview cards, or per-deck share metadata beyond the URL.
- A restyle of the landing/why/how pages; the explorer's visual direction applies to the explorer route. Sitewide restyle is out of scope.
- Performance claims. Any throughput or frame-rate claim requires a reproducible benchmark first.

# Context

The explorer is "the meat and potatoes" of the original site vision: making an impossibly large space feel like one continuous, addressable thing. Two constraints define it (decision 0007):

- `52! ≈ 8.07 × 10^67` cannot be a real scroll region and cannot be a JavaScript `number`. Position must be integer `bigint`.
- Unranking at scroll-frame rate belongs off the UI thread, behind the worker boundary the architecture already draws.

The domain is final and frozen (permutation domain plan): `unrankPermutation(CANONICAL_DECK, index)` maps any zero-based `bigint` index to a concrete ordering of card IDs `0..51`, and `permutationIndexToPublicDeckNumber` converts to the one-based public number. The explorer consumes only these.

Visual direction for the explorer is **minimal instrument** (decision 0007): dark neutral background and monospace deck numbers forming a precision frame around the decks. Within that frame, every deck is a fan of real playing cards — pips and court-card faces fully visible — because the cards themselves are the exhibit. This is a deliberate departure from the landing page's felt-table theme and is scoped to the explorer route.

# Proposed Changes

- **Worker layer** (`src/worker/`): a module worker exposing a typed request/response protocol. Request: `{ seq, startIndex: bigint, count: number }`. Response: `{ seq, startIndex, buffer }` where `buffer` is a transferable `Uint8Array` of `count * 52` card IDs. New requests supersede the in-flight one; responses with a stale `seq` are dropped by the client, and the worker cancels a superseded batch early. Within a batch the first deck is fully unranked and each subsequent deck is one `nextPermutation` step — see decision 0007. The worker imports only domain modules.
- **Virtualization layer** (`src/virtualization/`): pure, browser-independent functions for the anchor window. Owns a bounded physical window (row height × visible count + overscan) and the math to map `(anchorIndex: bigint, physicalOffset: number)` to a logical `bigint` deck index, and to recompute the anchor when the physical window scrolls far enough to recenter. Because each row renders 52 card faces, the physical window is kept small to bound DOM weight. All cross-window arithmetic in `bigint`; `number` only within one physical window.
- **Explorer UI** (`src/ExplorerPage.tsx` + styles): a scroll container hosting the physical window; rows rendered from worker batches; a jump-to-deck control; URL synchronization (`/deck/:number` or `?deck=`) with strict validation through `deck-number.ts`.
- **Playing-card rendering**: a UI-layer `PlayingCard` component renders each card ID as a real card face — corner rank/suit pips and a centered face design (court art for J/Q/K, pip layout for numbers) — and rows fan 52 of them left to right with overlap so all faces are visible. The domain stays numeric; card faces are pure presentation.
- **Nav**: add the explorer route to `SiteNav` and link the home page's "explorer is being built" copy to it.

# Test Plan

- **Virtualization (pure, Vitest):** anchor/offset → logical index round-trips; recentering keeps the same logical row stable; boundary behavior at index `0` and `52! - 1` (no negative anchor, no anchor past the last deck); window math never produces a `number` outside a single window.
- **Worker (Vitest with a mocked or real worker):** a batch request returns exactly `count` decks whose first deck equals `unrankPermutation(CANONICAL_DECK, startIndex)`; consecutive batches tile without gaps or overlaps; a superseded request's response is dropped; buffer length is `count * 52`.
- **Batch correctness against domain:** every card ID in a returned buffer is in `0..51`, and each 52-card group round-trips through `rankPermutation` to its expected index.
- **URL validation:** valid deck numbers load and anchor; `0`, `52! + 1`, non-numeric, and negative inputs are rejected by the domain before render.
- **UI (Vitest + Solid testing or Playwright if added):** scrolling requests new batches; jump control anchors to the requested deck; reduced-motion and rapid-scroll do not leave stale rows displayed.

# Security Considerations

- The deck-number URL parameter is untrusted input: strict `bigint` parse and bounds check through `deck-number.ts` before any render.
- The worker posts only flat numeric buffers; no DOM, no `importScripts`, no network. Worker code is bundled by Vite from first-party source — no remote scripts.
- No new runtime dependencies without recorded justification.

# Decisions Made

- Worker batching with transferable buffers, bigint virtualization, and deck-number URL addressing are recorded in decision 0007 before implementation.
- Explorer visual direction set to minimal instrument (decision 0007), scoped to the explorer route.
- Deck rows render real playing cards fanned left to right with all faces visible, not abstract glyphs — the cards are the exhibit (decision 0007 presentation section, refined with the human owner on 2026-08-29).
- The fan is dealt right-to-left: the face card sits rightmost and on top so the upright top-left pips read left to right, matching how a fresh deck spreads (refined with the human owner on 2026-08-29).
- Batch production uses the domain's `nextPermutation` to step between consecutive decks (unrank the first, step the rest) instead of a full factoradic unrank per deck; recorded in decision 0007 with correctness tests against `unrankPermutation`. Random access by deck number still unranked directly.

# Outcome

The explorer is live at `/explore`. A visitor can scroll a bounded physical window recentered over a logical `bigint` anchor spanning all `52!` decks, each row a fan of 52 real playing cards, and jump to any deck by its public number (shareable via `?deck=`). Computation runs in a Web Worker that unranked the first deck of a window and steps the rest with the domain's `nextPermutation`; stale batches are dropped by sequence and superseded batches cancel early. All quality gates pass.
