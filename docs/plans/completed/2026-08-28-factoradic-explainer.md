# Goal

Ship the "how it works" material that makes the site worth visiting before the full explorer exists: an interactive explainer of the ranking/unranking algorithm built from tiny decks of 2, 3, 4, and 5 cards, written once as application content and presentable in both normal documentation mode and full-screen talk mode.

# Non-Goals

- The 52-card virtualized explorer and its worker transport.
- The drag-and-drop editor (it links back to this explainer when built).
- A complete talk script or slide deck; this plan delivers the executable sections the talk is built from.

# Context

The site is launched but thin. The author wants the documentation side going as soon as possible, and the factoradic mapping is the heart of the project: it is why every deck is addressable without enumeration. Explaining it with 52 cards is hopeless on a screen; explaining it with 2–5 cards is concrete, exhaustive, and honestly more rigorous — every permutation of a 4-card deck fits in one table.

Thanks to decision 0005, the canonical deck's card IDs are sequential (`0..51`), so the explainer can use the real domain API with real card IDs as its symbols. Small-deck walkthroughs are literally `unrankPermutation([0, 1, 2, 3], index)` — the production code is the demo.

Architecture requires documentation claims about scale and behavior to be executable and reproducible. This plan makes the explainer the first consumer of that rule: every number, table, and step shown on the page is computed by the tested domain at render time, never hardcoded.

# Dependencies

- `src/domain/permutation.ts` (rank/unrank) and `src/domain/factorial.ts` exactly as tested today.
- The routing mechanism chosen by the Why page plan (shared navigation grows to include the explainer).
- Decision 0003 (factoradic indexing) is the reference being explained.

# Proposed Changes

- An explainer route (working name `/how`, finalized during implementation) structured as escalating sections:
  - **2 cards, 2 orderings** — the complete table; index 0 and index 1; the entire idea in miniature.
  - **3 cards, 6 orderings** — first non-trivial factoradic walkthrough: pick a digit, watch blocks of `2!` fall out; forward (unrank) and backward (rank) directions both shown step by step.
  - **4 cards, 24 orderings** — the complete 4×6 table, all generated by the domain at render time; a visitor can click any row to see its Lehmer-code digit selection replayed.
  - **5 cards, 120 orderings** — the moment enumeration stops being printable; introduce "blocks of `(n-1)!`" as the counting intuition and show the digit arithmetic for one arbitrary index like 73.
  - **Extrapolate to 52** — the same code, the same steps, with 52! standing in for the table; connect back to the `/why` atoms thought experiment and forward to the virtualized explorer.
- A step-through component that animates the shrinking selection pool and the accumulating index for any small index the visitor enters.
- The same sections render in a full-screen talk mode (large type, keyboard advance, one idea per screen) — the architecture already names talk mode as a `ui` boundary responsibility.
- Every table, digit row, and count on the page computed from the domain at render time; no hand-written permutation lists.

# Decisions Made

- Route is `/how` (with `/talk` for full-screen talk mode); nav grows to Home / Why? / How?.
- New pure domain module `src/domain/trace.ts` (`traceUnrank`) re-derives `unrankPermutation` while recording every factoradic digit, block size, running index, remainder, and pool snapshot — the UI renders exactly what the domain computed, never hardcoded steps. Exhaustively tested against production unrank through 8 values plus a representative 52-card index; output frozen.
- Explainer uses plain number symbols (0, 1, 2, …) for small decks — sequential card IDs (decision 0005) make the symbols literal card positions, and card art is a later rendering concern.
- Talk mode is a sibling `/talk` route outside the shared layout (full-screen, keyboard ←/→/space and button advance), reusing the exact same table and stepper components as `/how`.
- No new runtime dependencies; `@solidjs/router` was already adopted by the Why page work.

# Deviations

- Solid lint required restructuring both interactive components: prop reads at setup moved into `createMemo`/`createSignal` accessors (`props.size`, `props.index`).
- The stepper gained a controlled `index` prop so clicking a 4-card table row replays that exact index; `initialIndex` remains for uncontrolled defaults.
- Routing layout changed to a wildcard site route inside the shared `Layout` with `/talk` as a full-screen sibling. The first attempt (routes wrapped in `<Layout>` via children) passed typecheck, lint, and tests but rendered `[object Object]` — caught only by visual review. Final structure uses the documented @solidjs/router v1 pattern: `component={Layout}` with nested `<Route>` children, `/talk` as a top-level sibling. Lesson recorded: routing changes get a headless-browser screenshot check before claiming verification.
- Headless-Chrome screenshots of `/how` (both sections), `/talk`, and `/` were inspected after the routing fix; all render correctly.
